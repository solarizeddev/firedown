Add-ons

Prompted by a feedback note asking for userscripts. The answer proposed here is not a userscript engine of our own but Firefox add-ons, so that Violentmonkey (or Tampermonkey) brings userscripts with its own maintained GM_* API. This sheet answers three questions: which add-ons, where an add-on's button lives (not on the toolbar), and what in the app it touches. Dashed coral outline = new.

Rules

  • Which add-ons: anything Mozilla has signed. The main door is addons.mozilla.org's Android listing: the author declares Android support in the manifest (gecko_android), AMO signs it, and what fails on Android (sidebars, context menus, keyboard shortcuts, devtools) is filtered out before the user sees it. Firedown makes no compatibility judgement of its own and keeps no list.
  • A signed .xpi from anywhere else installs too (section 2b): an author's GitHub release, their own site, a file on the phone. Mozilla also signs add-ons it doesn't list, and Gecko checks the signature whatever the source, so Mozilla can still block a bad one later. Only the Android filter is lost, so Firedown reads the manifest and the prompt says when a file isn't made for Android.
  • Unsigned add-ons: never, and this GeckoView can't install them anyway. It is built from the 159.0 release tag, which Gecko's configure counts as release, so MOZ_REQUIRE_SIGNING is compiled in and xpinstall.signatures.required is a constant no pref can turn off (checked in firedown-geckoview and Firefox 159's source). Debug app builds use the same AAR. The only way in for unsigned code is ensureBuiltIn, which skips signing and the permission prompt: it stays for Firedown's own extensions, never for anything a user picks.
  • Built-in IDs are refused. Our uBlock is registered as uBlock0@raymondhill.net, its AMO ID. Installing it from AMO would replace the patched build and cut the native bridge (shield toggles, counts). Same for downloader@, youtube@, p2pshare@, icons@mozac.org: the install prompt says "Built into Firedown" and offers nothing to tap. Outside XPIs make this a real threat, not a mistake: our @solarized.dev IDs aren't registered on AMO, so Mozilla would sign an unlisted add-on that claims downloader@solarized.dev.
  • No toolbar icon, ever. The address bar is already shield · field · translate mark · reload. An add-on's button lives in the ⋮ sheet, on a second page, the way Firefox for Android's menu holds its extensions. GeckoToolbar is not touched at all.
  • Off in private tabs until the user switches it on per add-on (Firefox's default).
  • Said once, where it's decided: an add-on sees the pages you visit and runs outside Firedown's no-tracking promise. That sentence is on the install prompt and the Add-ons screen, nowhere else.
  • Discovery is the website, not a catalog. "Find add-ons" opens addons.mozilla.org/android in a tab. No AMO API client, no store screen to maintain.

1 · Where an add-on's button lives: the ⋮ sheet, one row, a second page

One new row, Add-ons, beside Translate in the first group, because both act on the page on screen. It is hidden until an add-on is installed (the Safe Folder row's rule: users who never install one see the sheet exactly as today). The row's trailing edge shows the installed add-ons' icons and, when any add-on sets a badge on this tab, the badge. A tap turns the sheet's page, the same two-page shape as "Where to back up". Each row there is that add-on's browser action (or page action), with its per-tab title, badge and enabled state. A tap runs the action, or opens the add-on's popup in a sheet.

2 · Installing: from AMO's Android site, one prompt

The user browses addons.mozilla.org/android in a normal tab (the "Find add-ons" row opens it). "Add to Firefox" ends in our prompt, which lists Gecko's own permission strings, the private-tab switch (off) and the one sentence about privacy. Our GeckoView turns off AMO's in-page install API (extensions.webapi.enabled false, set in firedown-geckoview's prefs so pages can't probe or trigger installs), so the button should fall back to a plain .xpi link: the same route as 2b. Check on a device; whatever arrives ends in WebExtensionController.install(), never in Downloads.

2b · A signed .xpi from anywhere else: a link or a file

Two doors, one pipeline. A tapped .xpi link is downloaded to the cache instead of to Downloads; "Install from file" copies the picked file there. Firedown then reads manifest.json out of the zip (ID, name, gecko_android, update_url) and refuses a built-in ID or a file that isn't an add-on before Gecko sees it. Then install() on the cached file (INSTALLATION_METHOD_FROM_FILE), and Gecko checks the signature. The prompt is section 2's, plus where the add-on came from and, when the manifest doesn't declare Android, a warning. Updates come only if the manifest names an update address; otherwise the add-on stays at that version until the user installs a newer file.

3 · The request itself: installing a userscript

This is why tabs.create has to work for add-ons. Violentmonkey catches a tap on a .user.js link and opens its own install page in a NEW tab. Today mTabDelegate.onNewTab refuses every tabs.create (on purpose: a returned session would be an untracked tab). For add-ons it opens a real tab through the tab repository, regular or private like the opener, and returns that tab's session. Built-in extensions stay refused.

4 · Settings → Add-ons

The door that always exists (General, under Translations), whether or not anything is installed. The list is grouped cards like every settings screen; built-in extensions are not listed (they're features, with their own settings). Detail: enable, private tabs, options page (opens in a tab: openOptionsPageInTab, else a full-screen page), permissions, version, remove. Updates are checked daily in the background; one that asks for new permissions waits on this screen for the user. "Install from file" is the second door of section 2b, and an add-on from outside the store says where it came from.

5 · What it touches

The honest list. Two lines are bugs the moment a user add-on runs, whatever the UI.

WhereTodayChange
BrowserSessionActionDelegateTreats EVERY onBrowserAction as uBlock's badge (onAdsCount).Bug as soon as an add-on sets a badge: it would overwrite the blocked count. Dispatch by extension.id: uBlock as today, anything else to a new AddonActions store (global action + per-session overrides, dropped with the tab).
mTabDelegate.onNewTabRefuses all tabs.create.Built-ins still refused. Add-ons get a tracked tab from the tab repository (opener's mode), its session returned. Without this Violentmonkey can't install a script.
mSessionTabDelegateonUpdateTab only to moz-extension:// (uBlock's blocked page).Unchanged for built-ins. Add-ons: http(s) and their own pages; add onCloseTab through the repository.
registerSessionWires built-ins' delegates into each session.Also action + tab delegates for each enabled add-on, and into every open session when one is installed or enabled (registerBuiltIn's late attach, again).
WebExtensionControllerNo prompt or add-on-manager delegate.setPromptDelegate (install / update / optional-permission prompts → sheets) and setAddonManagerDelegate (keeps an AddonRepository LiveData in step). Boot list() split on isBuiltIn; the orphan cleanup stays ID-specific.
GeckoComponents.onExternalResponseEvery response is a download.A .xpi (application/x-xpinstall, or the extension) from any https site goes to the cache and the add-on installer, never to Downloads. AMO's button should arrive here too, since its in-page install API is off (check on a device).
New: XpiInstaller—One pipeline for a link and a file: copy to cache, read manifest.json from the zip (bounded: the manifest only, size-capped), refuse built-in IDs and non-add-ons, then install(file, FROM_FILE). Gecko checks the signature. The cached file is deleted once installed or refused.
firedown-geckoview buildSigning required, compiled in.No change. Milestone 159.0 + no MOZ_REQUIRE_SIGNING override → Gecko's REQUIRE_SIGNING is a constant. A future build must not set MOZ_REQUIRE_SIGNING=0 or --with-unsigned-addon-scopes.
PopupBrowserSheetDialogFragmentThree groups.One row (hidden with no add-ons; the existing applyCorners pass handles it) and a second page. The places sheet already has the two-page pattern.
New: AddonPopupSheet—A sheet hosting a GeckoView for onOpenPopup's session. Not a tab, not persisted, closed on dismiss. The one genuinely new surface.
Settings—Door + list + detail fragments, on the card adapter like every screen, plus "Install from file" (the system picker, every type).
WorkManager—Daily unique addons-update → update() per add-on; a permission-adding update waits for Review.
Extension process watcherRestarts once, then a snackbar.Add-ons share the process with capture and uBlock, so a crashing add-on takes both down. On a second stop with add-ons enabled, the snackbar offers "Turn off add-ons".
GeckoToolbar—No change.
webrequests / parsers / uBlock—No change. Firefox hides one extension's own requests from the others, so add-ons can't see or break our probes. They do see the page's requests, as uBlock does.

6 · Open questions for the maintainer

Row hidden until an install, or always there?Proposed: hidden, with Settings → Add-ons as the permanent door (the Safe Folder rule). Always-there would be the discovery path, at a row's cost for everyone.
Any Android add-on, or Recommended only at first?Recommended (Mozilla-reviewed) cuts support load for a first release. Violentmonkey is Recommended; most userscript users would be covered either way. Proposed: any AMO Android add-on, the listing is the gate.
Pin one add-on to the toolbar?Proposed: no. The bar has no free slot, and a pinned glyph reopens the toolbar code this design avoids.
Content-blocker add-ons?A second ad blocker double-blocks and confuses the shield's count. Proposed: allowed, not detected (no reliable way to tell a blocker from its manifest). Revisit if reports come in.
A file not made for Android: warn or refuse?Proposed: warn and let the user decide. Plenty of add-ons work on Android without declaring it; the store's filter is stricter than the code.
Unsigned installs for developers?Settled by the build: this GeckoView can't install them, debug app builds included. A developer tests in Firefox Nightly, or signs an unlisted test build on AMO.
